# Digital Certificate Management Module — Design Spec

## Overview

Add a digital certificate management module to the CRM for issuing and managing X.509 licenses for hospital software products. The module handles the full lifecycle: ops personnel apply → two-level admin approval → certificate generation and download → expiry monitoring → renewal.

## Motivation

Hospitals run software on air-gapped internal networks. Annual maintenance fee collection is difficult. Digital certificates provide enforceable license expiration — the software warns on startup (within 2 years of expiry) or pops up random reminders (beyond 2 years), motivating hospitals to renew.

## Data Model

### Certificate Table

```sql
CREATE TABLE certificates (
    id              VARCHAR(36) PRIMARY KEY,
    cert_serial     VARCHAR(40) NOT NULL UNIQUE,        -- X.509 serial number
    customer_id     VARCHAR(36) NOT NULL,                -- FK → customers (hospital)
    product_name    VARCHAR(200) NOT NULL,               -- licensed software product
    start_date      DATE NOT NULL,                       -- validity start
    end_date        DATE NOT NULL,                       -- validity end
    status          VARCHAR(20) NOT NULL DEFAULT 'pending',
        -- pending | approved | rejected | active | expired | revoked
    applicant_id    VARCHAR(36) NOT NULL,                -- FK → users (ops who applies)
    approver_id     VARCHAR(36),                         -- FK → users (level-1 approver)
    final_approver_id VARCHAR(36),                       -- FK → users (level-2 approver, admin)
    reject_reason   TEXT,                                -- required when rejected
    certificate_pem TEXT,                                -- signed X.509 certificate
    private_key_pem TEXT,                                -- RSA private key (encrypted at rest)
    issued_at       DATETIME,                            -- when cert was generated
    expires_at      DATETIME,                            -- calculated from end_date
    revoked_at      DATETIME,
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id) REFERENCES customers(id),
    FOREIGN KEY (applicant_id) REFERENCES users(id),
    FOREIGN KEY (approver_id) REFERENCES users(id),
    FOREIGN KEY (final_approver_id) REFERENCES users(id)
);
```

### Status Flow

```
pending ──[level-1 approve]──> approved ──[level-2 approve + cert gen]──> active
   │                                │
   └──[reject]──> rejected          └──[revoke]──> revoked

active ──[end_date passed]──> expired
expired ──[renew (creates new pending record)]──> pending
```

**Two-Level Approval:**
1. **Level 1** (any admin): `pending` → `approved`, sets `approver_id`. Cannot be the applicant.
2. **Level 2** (admin, must be different from level-1 approver): `approved` → `active`, generates RSA key pair + X.509 cert, encrypts and stores private key, sets `final_approver_id`.

## Certificate Generation

### Algorithm
- RSA 2048-bit key pair
- X.509 v3 certificate, SHA-256 signing
- PEM-encoded output

### Certificate Content
- **Subject CN**: hospital name (customer name)
- **Subject OU**: product name
- **Serial number**: unique, generated by CRM
- **Validity**: `not_before` = start_date, `not_after` = end_date
- **Extensions**: Basic Constraints (CA:FALSE), Key Usage (digital signature)

### Library
- Python `cryptography` package (`cryptography.x509`, `cryptography.hazmat.primitives`)

### Storage
- Private key: AES-encrypted before DB storage using a server-side secret (from settings/config)
- Certificate: stored as plain PEM text (public information)
- On download: decrypt private key, bundle into .zip with certificate

### Renewal
- Each renewal generates a new key pair and certificate
- New `pending` record is created; old cert stays active until new one is approved
- Approved old cert stays valid until its end_date; status may overlap

## API Design

| Method | Path | Description | Permission |
|--------|------|-------------|------------|
| GET | `/api/certificates` | List certificates (filter: status, customer_id, date range) | certificates |
| POST | `/api/certificates` | Create application (status=pending) | certificates |
| GET | `/api/certificates/{id}` | Get certificate detail | certificates |
| GET | `/api/certificates/{id}/download` | Download .zip (cert + private key) | certificates |
| POST | `/api/certificates/{id}/approve` | Approve (level-1: pending→approved, level-2: approved→active+cert gen) | certificates + admin |
| POST | `/api/certificates/{id}/reject` | Reject (requires reject_reason) | certificates + approver role |
| POST | `/api/certificates/{id}/revoke` | Revoke active cert | certificates + admin |
| POST | `/api/certificates/{id}/renew` | Initiate renewal (creates new pending) | certificates |

### Approve Endpoint Behavior

Same endpoint handles both levels, determined by current status:

**Level 1** (status = `pending`):
1. Verify current user is admin and not the applicant
2. Set status to `approved`, record `approver_id`

**Level 2** (status = `approved`):
1. Verify current user is admin and not the level-1 approver
2. Verify current user is not the applicant
3. Generate RSA 2048-bit key pair, sign X.509 cert
4. Encrypt private key with server secret, store in DB
5. Store certificate PEM in DB
6. Set status to `active`, record `final_approver_id`, `issued_at` = now

### Download Endpoint Behavior
1. Status must be `active`
2. Decrypt private key from DB
3. Bundle `certificate.pem` + `private_key.pem` into a .zip file
4. Return as attachment download
5. Re-download is allowed (decrypts from DB each time)

## Hospital-Side Verification Scheme

### Embedded Artifact
The hospital software ships with the CRM's **CA public key** embedded at build time.

### Verification Flow (on software startup)
1. Read installed `certificate.pem` from local filesystem
2. Verify certificate signature against embedded public key
3. Check current system time against `not_before` / `not_after`
4. Determine action:
   - **Valid**: proceed normally, no UI interruption
   - **Expired < 2 years** (730 days): show warning dialog on startup, software continues normally after dismiss
   - **Expired ≥ 2 years**: show warning dialog on startup, and randomly display a reminder popup during use (approximately once per 20 session-hours, e.g., 5% chance every hour). Software continues to function.

### Certificate File Format
Single PEM file containing the X.509 certificate. The hospital software only needs the certificate (public), not the private key. The private key stays in the CRM and is used for certificate signing only.

### Python Verification Example (for hospital software)
```python
from cryptography import x509
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.x509.oid import NameOID
import datetime

def verify_certificate(cert_path: str, ca_public_key_pem: bytes) -> bool:
    """Returns True if certificate is valid and signed by CA."""
    with open(cert_path, "rb") as f:
        cert = x509.load_pem_x509_certificate(f.read())
    ca_key = serialization.load_pem_public_key(ca_public_key_pem)
    # Verify signature
    ca_key.verify(
        cert.signature, cert.tbs_certificate_bytes,
        padding.PKCS1v15(), cert.signature_hash_algorithm,
    )
    # Check validity period
    now = datetime.datetime.utcnow()
    if now < cert.not_valid_before_utc or now > cert.not_valid_after_utc:
        raise ExpiredError(cert.not_valid_after_utc)
    return True
```

### Random Popup Logic (for hospital software)

```
IF cert_expired_days > 730:
    ON_STARTUP: show mandatory warning dialog
    DURING_USE: hourly random check
        IF random() < 0.05: show popup reminder
ELIF cert_expired_days > 0:
    ON_STARTUP: show warning dialog (single dismiss)
```

## Frontend Pages

### Certificate List Page (`/certificates`)
- Table with columns: serial, hospital name, product, validity dates, status tag, applicant
- Status tags: pending (yellow), active (green), expired (red), rejected (gray), revoked (dark gray)
- Filters: status dropdown, customer search, date range
- Actions per row based on status:
  - pending: approve/reject (if approver role)
  - active: download, revoke (if admin)
  - expired: renew

### Certificate Application Form (Drawer)
- Customer dropdown (select hospital)
- Product name text input
- Start date (date picker, default today)
- Duration (select: 3/6/12/24/36 months, default 12)
- End date (auto-calculated, display only)
- Submit → POST /api/certificates

### Approval Page / Inline Actions
- Approve: button on list row → calls POST /api/certificates/{id}/approve
- Reject: dialog with required reason textarea → calls POST /api/certificates/{id}/reject
- Revoke: confirmation dialog → calls POST /api/certificates/{id}/revoke

## Permission Integration

### Permission Key: `certificates`

1. **Router** (`router/index.js`): Add `/certificates` route, `Certificates: 'certificates'` in menuMap, `'certificates': '/certificates'` in permissionToPath

### Access Control
- Admin: always has access
- Non-admin: needs `certificates` in their `menu_permissions` array

## Deployment Notes

- Requires `cryptography` Python package (may need `pip install cryptography`)
